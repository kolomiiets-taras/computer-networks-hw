
### Відповіді

- **Default route:** `default via 192.168.20.1 dev wlp0s20f3`
- **Мережевий інтерфейс:** `wlp0s20f3` (Wi-Fi-адаптер)

### Що означає `default via ...`

`default` — це маршрут для всіх адрес, для яких у таблиці немає точнішого запису (те саме, що `0.0.0.0/0`). `via 192.168.20.1` — пакет треба передати не напряму одержувачу, а **шлюзу** — домашньому роутеру, який знає, куди його переслати далі. Тобто правило звучить так: «усе, що не в моїх локальних мережах, відправляй на роутер `192.168.20.1` через інтерфейс `wlp0s20f3`».

### Як система обирає маршрут

Для кожного пакета ядро шукає в таблиці запис із **найдовшим збігом префікса** (longest prefix match) — найточніший:

| Куди йде пакет | Який маршрут спрацює | Чому |
|---|---|---|
| `192.168.20.50` (пристрій у моїй Wi-Fi мережі) | `192.168.20.0/24 dev wlp0s20f3` | Префікс `/24` збігається. Шлюзу немає (`scope link`) — пакет іде напряму |
| `172.17.0.2` (Docker-контейнер) | `172.17.0.0/16 dev docker0` | Префікс `/16` збігається — пакет іде в міст Docker |
| `140.82.121.4` (github.com) | `default via 192.168.20.1` | Жоден точний маршрут не підходить, `/0` збігається з будь-якою адресою |

Інші поля першого рядка: `proto dhcp` — маршрут отримано від DHCP-сервера роутера; `src 192.168.20.185` — з якою адресою відправника виходять пакети; `metric 600` — пріоритет (якби було два маршрути за замовчуванням, наприклад Wi-Fi і кабель, переміг би той, у кого метрика менша).

Записи `172.17–172.22.x.x` створив Docker для своїх мостових мереж. Позначка `linkdown` — у цій мережі зараз немає запущених контейнерів.

### Відповіді

1. **Три основні ланцюги таблиці `filter`:** `INPUT`, `FORWARD`, `OUTPUT`. Решта (`DOCKER`, `DOCKER-USER`, `DOCKER-FORWARD` тощо) — користувацькі ланцюги, які створив Docker. Вони не обробляють пакети самі: у них переходять із вбудованого ланцюга `FORWARD` (target `DOCKER-USER`, `DOCKER-FORWARD`).
2. **Default Policy ланцюга INPUT:** `ACCEPT`. Правил в INPUT немає, тому всі вхідні пакети для цього комп'ютера пропускаються. На робочій станції за NAT домашнього роутера це прийнятно, але на сервері в інтернеті так робити не можна — там політику ставлять `DROP` і явно дозволяють лише потрібні порти.

### Різниця між INPUT і FORWARD

Ядро дивиться на адресу призначення пакета і вирішує, в який ланцюг його відправити:

```text
                     ┌──────────────────────────┐
пакет приходить ──►  │ адреса призначення —     │
                     │ цей комп'ютер?           │
                     └──────┬─────────────┬─────┘
                        так │             │ ні
                            ▼             ▼
                         INPUT         FORWARD ──► виходить через інший інтерфейс
                            │
                            ▼
                    локальний процес
                            │
                            ▼
                         OUTPUT ──► пакет, який створив сам комп'ютер
```

- **INPUT** — пакети, адресовані **самому цьому комп'ютеру**: наприклад, хтось із локальної мережі підключається до мого SSH або до порту 3000. Ланцюг вирішує, чи пустити пакет до локального процесу.
- **FORWARD** — пакети, які **проходять транзитом**: прийшли через один інтерфейс і мають вийти через інший, а цей комп'ютер для них лише маршрутизатор. Саме так працює трафік Docker: пакет з інтернету до контейнера проходить через хост (`wlp0s20f3` → `docker0`), але адресований не хосту, а контейнеру.
- **OUTPUT** — пакети, які створив сам комп'ютер і відправляє назовні.

Тому в моїй системі INPUT порожній, а **FORWARD має політику `DROP`** і заповнений правилами Docker. Docker ставить `DROP`, щоб ніхто не міг потрапити в контейнери в обхід правил. Далі він явно дозволяє лише потрібне:
- `DOCKER-CT` — пропускає відповіді на вже встановлені з'єднання (`ctstate RELATED,ESTABLISHED`);
- `DOCKER` — пропускає нові з'єднання тільки на опубліковані порти: `ACCEPT ... 172.17.0.3 tcp dpt:80` — це якраз мій nginx із завдання 4. Решту — `DROP`;
- `DOCKER-USER` — порожній ланцюг для власних правил адміністратора. Docker його не чіпає, тому сюди можна, наприклад, додати заборону доступу до контейнерів з певних IP.

Примітка: у рядках `DROP` і `ACCEPT` без адрес насправді є умови на мережеві інтерфейси (`-i docker0`, `-o br-...`). Ключ `-L -n` їх не показує, для цього потрібен ще `-v`.

### Відповіді

1. **IPAddress контейнера:** `172.17.0.2` (маска `/16`, `IPPrefixLen: 16`)
2. **Docker network:** `bridge` — стандартна мережа Docker, якій на хості відповідає міст `docker0`. Шлюз контейнера — `172.17.0.1`, тобто адреса самого хоста на мосту `docker0` (видно і в `ip route` із завдання 1: `172.17.0.0/16 dev docker0 ... src 172.17.0.1`).

### Як Docker ізолює мережу контейнера

- **`SandboxKey: /var/run/docker/netns/5322066dbaf4`** — це окремий **network namespace** контейнера. Усередині нього свій набір інтерфейсів, своя таблиця маршрутів і свої правила firewall. Процес nginx у контейнері бачить лише свій інтерфейс `eth0` з адресою `172.17.0.2` і не бачить ні `wlp0s20f3`, ні інших мереж хоста.
- Зв'язок з хостом забезпечує **пара veth**: один кінець — `eth0` всередині контейнера, другий — інтерфейс `veth...` на хості, підключений до мосту `docker0`. Міст працює як віртуальний комутатор: усі контейнери в мережі `bridge` бачать один одного через нього.
- **`"Ports": {"80/tcp": null}`** — nginx слухає порт 80, але цей порт **не опубліковано** на хості (`null`). Тобто до цього контейнера можна дістатися лише з самого хоста або з інших контейнерів у цій мережі. Перевірка з хоста працює, бо хост підключений до `docker0`:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://172.17.0.2
```
```text
200
```

### Чому IP контейнера недоступний з інтернету

1. **Це приватна адреса.** `172.17.0.0/16` входить у приватний діапазон `172.16.0.0/12` (RFC 1918). Маршрутизатори в інтернеті такі адреси не пересилають, тож пакет на `172.17.0.2` з інтернету просто нікуди не дійде.
2. **Мережа існує лише всередині хоста.** Міст `docker0` — віртуальний, і про мережу `172.17.0.0/16` знає лише таблиця маршрутів мого комп'ютера. Навіть мій домашній роутер не знає, що за адресою `192.168.20.185` є ще якась мережа контейнерів.
3. **Двоступеневий NAT.** Контейнер виходить в інтернет через MASQUERADE на хості (адреса `172.17.0.2` → `192.168.20.185`), а далі — через NAT домашнього роутера (`192.168.20.185` → публічна IP). Зовні видно лише публічну адресу роутера.
4. **Firewall.** Навіть якби пакет якось дійшов до хоста, ланцюг `FORWARD` з політикою `DROP` пропускає в контейнери лише трафік на явно опубліковані порти (завдання 2).

Щоб сервіс у контейнері став доступним ззовні, порт треба опублікувати через `-p` — це завдання 4.

Інші три правила `DNAT` — для інших контейнерів на моєму комп'ютері (PostgreSQL, Redis і веб-застосунок), опублікованих так само.

### 3. Як Port Mapping дозволяє зовнішньому клієнту дістатися контейнера

Шлях запиту від клієнта з локальної мережі (наприклад, телефона `192.168.20.50`) до nginx:

```text
Клієнт 192.168.20.50
   │  TCP SYN → 192.168.20.185:8080
   ▼
wlp0s20f3 хоста
   │  nat / PREROUTING: адреса призначення локальна (dst-type LOCAL) → ланцюг DOCKER
   │  nat / DOCKER: DNAT  192.168.20.185:8080 → 172.17.0.3:80
   ▼
маршрутизація: 172.17.0.3 тепер не адреса хоста → пакет іде у FORWARD, а не в INPUT
   │  filter / FORWARD → DOCKER: ACCEPT  tcp dpt:80 до 172.17.0.3
   ▼
docker0 → veth → eth0 контейнера
   │
   ▼
nginx у контейнері (172.17.0.3:80) отримує запит від 192.168.20.50
```

Відповідь іде назад тим самим шляхом. Модуль **conntrack** ядра пам'ятає, що це з'єднання пройшло через DNAT, і автоматично замінює адресу відправника відповіді `172.17.0.3:80` назад на `192.168.20.185:8080`. Тому клієнт бачить відповідь саме від тієї адреси, до якої звертався, і нічого не знає про контейнер.

Логіка коротко:
1. Контейнер ізольований: його адреса `172.17.0.2/3` приватна і доступна лише всередині хоста (завдання 3).
2. Port Mapping відкриває «двері» на зовнішній адресі хоста: порт 8080 хоста.
3. **DNAT** в таблиці `nat` переписує адресу призначення кожного вхідного пакета з `хост:8080` на `контейнер:80`.
4. Після DNAT пакет адресований контейнеру, тому він потрапляє в ланцюг `FORWARD`, де правило Docker `ACCEPT ... dpt:80` його пропускає.
5. **conntrack** робить зворотну заміну для відповідей.
6. Контейнер при цьому залишається ізольованим: доступний лише один порт, який я явно опублікував, а не весь контейнер.

```text
172.17.0.1 - - [27/Oct/2026:16:44:43 +0000] "GET / HTTP/1.1" 200 896 "-" "curl/8.5.0" "-"
192.168.20.185 - - [27/Oct/2026:16:50:38 +0000] "GET / HTTP/1.1" 200 896 "-" "curl/8.5.0" "-"
```

- **Запит через `192.168.20.185:8080`** пройшов через **DNAT** (з самого хоста пакет проходить ланцюг `nat / OUTPUT` замість `PREROUTING`, але потрапляє в той самий ланцюг `DOCKER` і те саме правило). Nginx бачить справжню адресу клієнта `192.168.20.185`, бо DNAT змінює лише адресу **призначення**, а адресу відправника залишає.
- **Запит через `localhost:8080`** (завдання 4.1) пройшов інакше: nginx бачить відправника `172.17.0.1` (адресу хоста на `docker0`). Причина в правилі ланцюга `OUTPUT`: `DOCKER ... !127.0.0.0/8` — DNAT **не** застосовується до адрес `127.x.x.x`. Такі з'єднання приймає процес `docker-proxy`, який слухає порт 8080 на хості і сам відкриває нове з'єднання до контейнера:

```bash
ps -eo pid,user,args | grep docker-proxy.*8080
```
```text
2080329 root     /usr/bin/docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8080 -container-ip 172.17.0.3 -container-port 80 -use-listen-fd
```

Тобто Docker використовує два механізми: iptables DNAT для трафіку ззовні і userland-proxy для `localhost`, бо ядро за замовчуванням не маршрутизує пакети з адресою `127.0.0.1` на інші інтерфейси.

## Завдання 5. Архітектура Kubernetes: Pod vs Service

### 1. Чому контейнери в одному Pod спілкуються через localhost

Усі контейнери одного Pod **ділять один network namespace**. Kubernetes спершу запускає службовий контейнер `pause`, який створює namespace і тримає його. Потім кожен контейнер Pod підключається до **того самого** namespace, а не отримує власний, як у Docker із завдання 3.

Через це в Pod:
- один мережевий інтерфейс і **одна IP-адреса** на всі контейнери;
- один спільний `lo` (loopback), тобто `localhost` у всіх контейнерах — це той самий інтерфейс;
- спільний простір портів: якщо контейнер `app` слухає порт 8080, контейнер `sidecar` у тому самому Pod дістанеться до нього через `localhost:8080`. Через це два контейнери в одному Pod не можуть слухати один і той самий порт.

З погляду мережі контейнери Pod поводяться як процеси на одному комп'ютері. Так працюють sidecar-контейнери: проксі Envoy в Istio, збирачі логів, які звертаються до основного застосунку через `localhost`.

### 2. Навіщо Service (ClusterIP), якщо в кожного Pod є своя IP

Бо IP Pod **нестабільна**, а Pod-и **тимчасові**:
- Pod перестворюється при оновленні Deployment, падінні, переїзді на іншу ноду — і кожен новий Pod отримує **нову IP**;
- зазвичай одночасно працює кілька реплік (наприклад, 3 Pod-и бекенду) — клієнту незрозуміло, на яку з трьох IP звертатися;
- кількість Pod змінюється при масштабуванні (HPA).

Якби фронтенд звертався до бекенду за IP Pod, він ламався б при кожному деплої.

**Service** вирішує ці проблеми:
- **Стабільна віртуальна IP (ClusterIP)** і **DNS-ім'я** (`billing.default.svc.cluster.local`), які не змінюються весь час існування Service;
- Service знаходить свої Pod-и за **label selector** (наприклад, `app: billing`) і автоматично відстежує їхні поточні IP через об'єкт `EndpointSlice`. Новий Pod з потрібною міткою одразу додається, а Pod, що впав або не проходить readiness-перевірку, прибирається;
- **балансування навантаження** між усіма репліками.

ClusterIP доступна лише всередині кластера. Для доступу ззовні використовують типи `NodePort`, `LoadBalancer` або `Ingress`.

### 3. Роль kube-proxy

ClusterIP — **віртуальна** адреса: жоден інтерфейс і жоден процес не слухає на ній. Щоб пакети на неї кудись доходили, на **кожній ноді** кластера працює **kube-proxy**:

1. Стежить через API-сервер Kubernetes за всіма Service та їхніми EndpointSlice (актуальний список IP Pod-ів).
2. Перетворює їх на правила ядра Linux. У режимі `iptables` (або сучасному `nftables`) це **ті самі DNAT-правила, що й у Docker у завданні 4**: «пакет на `ClusterIP:80` → DNAT на `IP_одного_з_Pod:8080`». Pod обирається випадково, і так виходить балансування.
3. Оновлює правила одразу, щойно Pod з'являється, зникає або змінює IP.

Тобто kube-proxy сам трафік не пропускає через себе (у режимах iptables/nftables/IPVS): він лише налаштовує ядро, а пакети переписує ядро. Завдяки цьому клієнт завжди звертається на стабільну ClusterIP, а kube-proxy гарантує, що за нею — лише живі Pod-и.

Аналогія з Docker: `-p 8080:80` створює одне DNAT-правило на одному хості до одного контейнера; kube-proxy робить те саме, але на всіх нодах кластера, для всіх Service і з балансуванням між багатьма Pod-ами.
